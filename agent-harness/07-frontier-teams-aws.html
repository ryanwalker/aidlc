Core Thesis

It wasn't about the tools, it was about the way that they worked. — Clare Liguori, on why half the pilot teams saw 3x and half saw 4.5x+

Teams that achieved step-function gains intentionally changed how they worked. Teams that saw little improvement layered the same tooling on top of an unchanged workflow. The differentiator was practice, not product — roughly 90% of both groups used the same tools.

Liguori notes that across inline completion → chat → vibe coding, she personally only ever felt 10–20% more productive. The frontier practice is presented as a different category of change, not more of the same.

Three defining behaviors of a "frontier developer"

  • Hands-off coding — they personally write roughly 1–2% of the code they ship; agents produce the rest
  • Infrequent interaction — the goal is an agent running for hours at a stretch without intervention
  • Minimized idle time — multiple agents running in parallel against a task backlog

Metric worth noting: the Stores pilot measured deployment velocity to production, not commit count — how fast changes actually reach customers. The two earlier cases leaned on commit history, which is a considerably weaker proxy.

Interviews across all three groups produced the five habits below. Liguori is deliberate about the word habits: the finding was about sustained daily practice, not a one-time sprint configuration.

The Five Habits

1 · Invest in agent context

Engineers carry large amounts of implicit context and transfer it to people through Slack, onboarding, mentorship, code review, and sprint planning. For agents it has to be written down. Two questions became standing habits:

  • After every agent mistake — "What am I missing in my steering files?" A wrong output is treated as a missing-context signal, so the fix removes the whole class of error instead of correcting it turn by turn.
  • After every model release — "Do I still need this, or is it just bloating context?" Her example: Sonnet 3.7 required piles of "do not" rules that were largely unnecessary by Opus 4.5.
The second question is the less obvious one. Context is framed as an asset with a pruning cycle, not an append-only file. Prohibition-shaped content ages fastest, because it encodes workarounds for model weaknesses that later models don't have.

2 · Slow down to speed up

In almost every team that was interviewed, they reported that their productivity actually went down as they intentionally adopted a new way of working. — Clare Liguori

Presented as planned, scheduled engineering work rather than something that happens opportunistically:

  • Build agent context — the Habit 1 investment
  • Improve existing tools' error messages — so the model can tell what went wrong when something fails
  • Build new tools and MCP servers — so the agent can actually complete the task
  • Restructure the codebase — so agents can navigate it
  • Change programming language — the drastic end of the range

On the last point: teams struggled with untyped languages because there is no compiler signal, so the model guesses and hands the guess back. Liguori has seen moves to TypeScript, and notes Rust has become popular inside Amazon partly for the quality of its compiler errors. She is explicit that this is optional, not prescribed.

3 · Feed agents, don't babysit

The mechanism behind the step-function gain. If you are in a conversational loop all day, you are the validator on every turn — waiting 30–60 seconds per generation, unable to do anything else, and therefore unable to run agents in parallel.

Babysitting — lots of back and forth

  • Add authorization to this API
  • Add tests
  • The tests don't pass
  • The tests still don't pass
  • We don't have enough test coverage
  • Add integration tests
  • The integ tests don't pass

Feeding — what to do + how to validate

Add authorization to this API. Add unit tests. Run the unit tests; ensure they pass and achieve 90% coverage for the new code. Add integ tests to validate authorization and ensure they pass.

The task is identical. What changed is that the action, the verification step, and the numeric bar all moved into the prompt up front. Critically, nothing on the right is information the developer lacked on turn one of the left — it simply hadn't been stated.

The left column's failures aren't the agent performing badly; they're the agent having no way to know it was finished. Every "the tests don't pass" is a signal a human had to carry because nothing instructed the agent to check for itself.

The compounding step: once a validation prompt stabilizes, move it into the steering file so it applies every time without being typed. That is Habit 1 consuming the output of Habit 3.

4 · Make intent explicit

The vibe-coding failure mode is a high-level prompt, a large volume of generated code, then a long negotiation — that's not what I meant, the requirements are wrong, I didn't want it built that way.

It is less productive to iterate with the agent on code when the intent itself was incorrect. — Clare Liguori

For ambiguous or complex features, teams write a specification first — generated by the model rather than hand-written, but reviewed before implementation. The stated reason: iterating with a model on a document is far easier than iterating on code changes spread across a codebase.

# Feature Specification

## Objective
What is the main objective or purpose of the project

## Use Cases
Who are the users and how will they use the feature

## Key Functionality
What are the key elements, style, and design approach required

## Technical Requirements and Design
What specific technical or quality requirements must be met and how
should the feature be implemented

The ordering carries the argument: why → who → what → how, with technical design last. The vibe-coding loop jumps straight to "how," so when the real disagreement is about "what" or "why," it gets relitigated against code that already exists. Note also that the final section is where Habit 3's validation criteria naturally live.

5 · Shift testing left

The purpose is a fast, local feedback loop — the thing that makes hours-long autonomous runs possible. The agent will make mistakes; that is acceptable as long as the signals exist for it to self-correct.

  • Linters — cheapest and fastest signal, listed first
  • Mock services — listed second, above the test types
  • Unit tests, integration tests, performance tests, security tests

Mock services get unusual prominence. Rather than running integration tests end-to-end against live services, teams invested in local mocks with deterministic responses so everything runs on the laptop with no cloud spin-up. More speed means more loops per unit time, which is the actual constraint on agent productivity.

These are all things we all know we should have been doing all along. This is good engineering hygiene. But now the ROI is, I think, finally high enough for us to actually invest in it. — Clare Liguori

What Is Still Hard

Liguori explicitly declines the "adopt these five and reach nirvana" framing, and the caveats are arguably the most transferable part of the talk.

Burnout

  • FOMAT — Fear Of Missing Agent Time (a term she credits to someone else). Engineers stay up late trying to land a prompt good enough to run overnight, so a finished change is waiting in the morning. The agent's clock runs continuously, so idle agent capacity starts to feel like waste — the machine's availability begins setting the human's schedule.
  • Cognitive load rises with parallelism — constant context-switching between terminal tabs. This is the direct cost of the Habit 3 payoff.
  • Review can be harder than writing, and it lands unevenly. Senior engineers have spent years building the review muscle; early-career engineers have not. The model asks the people with the least-developed review skills to do the most reviewing.

Organizational change

  • Accepting "slow down to speed up." Liguori includes herself among leaders guilty of asking why teams aren't faster now that the tools exist. Teams need roughly two months to invest in the codebase and change habits — measured against social-media claims of 20 PRs a day, that looks like failure.
  • Going too broad, too fast. Had Amazon mandated frontier practice everywhere at once, the learnings from the pathfinder, sprint, and pilot phases wouldn't exist. Scaling from ~50 teams to the next ~2,000 is described as the 2026 problem.
  • New bottlenecks appear. Writing code used to be the constraint; now it's decision-making and launch-review process.
The bottleneck arithmetic: when a product took 9–12 months to build, spending two months deciding to build it and two months approving the launch was rounding error. When the code takes 1–2 months, those approvals become the critical path. Liguori's observation is that frontier teams spend more time making decisions than writing code — so the leverage moves to making fast decisions, especially reversible ones.

Cross-Cutting Pattern: Governance by Document

Habits 1, 3, and 4 are the same move applied at different points: stop adjudicating individual agent actions, start writing down the rules those actions are judged against. Correction shifts from runtime to the document.

This is why the five reinforce each other rather than standing as independent tips:

  • Habit 4 writes down what is being built — before code exists to argue about
  • Habit 3 writes down what "done" means — so the agent self-gates
  • Habit 5 builds the machinery that checks it — so self-gating is possible at all
  • Habit 1 promotes recurring cases into permanent context — so nothing is retyped
  • Habit 2 is the admission that all of the above is real, schedulable work

A constitution is a tempting analogy, and it holds in one dimension: both are written principles applied in advance to an actor whose every action can't be supervised. Kiro's steering-file inclusion modes even reproduce a legal hierarchy — always behaving like constitutional law and fileMatch like statute that binds only within its jurisdiction. But the analogy breaks on amendment cost. A constitution's defining feature is being hard to change; Habit 1 says to delete aggressively. Agent context behaves more like case law that gets overturned as the underlying court changes.

Distinct from Constitutional AI, which applies written principles at training time to shape weights. Steering files operate at inference time — they cost tokens on every request and compete with everything else in the window.

Reference: Kiro Steering Files

The talk uses "steering files" and "skills files" interchangeably without defining either. For clarity — steering files are Kiro's persistent project-context mechanism, the analogue of CLAUDE.md. They live in .kiro/steering/ as markdown, and three are generated by default: product.md (purpose and goals), tech.md (frameworks and constraints), and structure.md (code organization).

YAML front matter controls when each file loads, and must be the first content in the file:

ModeLoadsIntended for
inclusion: alwaysEvery interactionCore standards, tech stack, conventions
inclusion: autoWhen the request matches its descriptionContext-heavy guidance needed only sometimes
inclusion: fileMatch + fileMatchPatternOnly when working on matching files (globs; arrays allowed)Domain-specific standards

Additionally, #[[file:<relative_path>]] pulls in live workspace file contents, and CLI custom agents can load the directory via {"resources": ["file://.kiro/steering/**/*.md"]}.

Why this matters for Habit 1: the inclusion modes make "is this just bloating context?" a mechanical question rather than a judgment call. Bloat comes from always files — a rule that only applies to React components costs nothing elsewhere if it's fileMatch-scoped. Much of "should I delete this?" becomes "should I demote this to conditional?"

Relevance

This is the first source in this collection with controlled internal data across a normal team distribution rather than practitioner advocacy — 50 teams, brownfield codebases, measured on deployment velocity rather than commit volume. The split result (under 3x vs. median 4.5x with identical tooling) is the strongest available evidence that harness practice, not tool selection, is the variable that matters.

Habit 1's pruning question is a direct counterweight to the Ratchet Principle in 02 · Harness Engineering. The ratchet says every failure becomes a permanent rule; this talk says rules encoding old model weaknesses become liabilities and must be actively removed. Both are right, and the synthesis — every rule traces to a specific failure, and gets re-examined when the model changes — is a more complete policy than either alone.

Habit 2 gives a name and internal precedent to the adoption cost documented in specs/adoption-plan.md: the productivity dip is not a sign of failed rollout, it is the expected shape. The organizational caveats — leaders reading the dip as underperformance, and rolling out too broadly before best practices exist — are the most directly applicable material here for anyone planning a phased adoption.

Habit 5's emphasis on deterministic local mock services is the concrete, unglamorous infrastructure investment that makes long autonomous runs viable, and pairs with the hook-based enforcement already scaffolded in harness/.
